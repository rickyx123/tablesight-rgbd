# 边缘部署与工程可靠性

## 部署链

PyTorch PT → 固定形状 ONNX → ATC 转 OM → Ascend 推理。每次检查类别顺序、输入尺寸、RGB/BGR、归一化、letterbox、输出布局、坐标还原和 NMS。

三后端核对既看类别，也看同图预测框 IoU 和置信度差。历史不同模型阶段存在不同耗时，不把早期模型或纯推理段的数字直接贴到最终 V9 系统上。

## 时间预算

冷启动、模型预热、相机对齐、有效采样、后台深度、OCR 和通信分别记账。将模型初始化搬到持久 worker 能改善重复启动体验，但应同时记录冷启动成本。

深度任务从前台采样中移到有界后台队列，队列保存自己的同序号数据，不能在处理第 n 帧时读取已经被覆盖的最新画面。过度并发会使 OCR、深度与 UI 争用 CPU，形成积压与结果延迟。

## 启动失败与有限降级

高清对齐失败不应让整场比赛直接退出。历史方案加入有限重试与原生 640 兼容采集，保留可用检测/深度并关闭不可靠的高清 OCR。图像显示状态、OCR 是否关闭和本次降级原因应进入记录。

这是针对特定故障的降级策略，不等于可以在相机缺失时生成虚构识别结果。

## 正式三桌编排

开始信号应与耗时的模型准备分离。第二轮按方桌1 → 方桌2 → 圆桌编排，视觉采样与转向等待有各自的时钟。

云台没有真实到位反馈时，采用最小固定等待和有上限的辅助稳定判断。旋转圆桌不能因为物品持续运动而被要求整幅画面完全静止。

通信失败后可以保存已完成的本地识别结果；没有转向能力时不能假装已经识别另外两桌。发送完成与裁判端确认接收也应分开描述。

## 保持可回退

- 新模型独立命名并保存 SHA，切换配置而非覆盖旧权重。
- 编号文件名和实际模型内容可能不一致，最终核对内容、配置与调用链。
- 对算法文件、配置、入口和依赖建立快照；单独记录本次改变的范围。
- 日志和结果画面要使用一致的帧与筛选规则，避免“预览红框、最后还计数”的错觉。
- 清空结果应限定在明确目录并检查占用，模型和证据备份不属于清空范围。

仓库不提供真实网络地址、账号口令和可直接触发比赛设备的入口。需要恢复硬件部署时，先按原设备环境核对。
